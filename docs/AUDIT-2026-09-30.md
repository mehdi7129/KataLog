# KataLog — audit complet du 30 septembre 2026

**Périmètre : analyse et préparation du développement.** Aucun changement de
comportement de l'app, aucune migration, publication ou modification de GCS dans
cet audit. Les travaux de distribution déjà présents sont conservés.

## 1. Conclusion

La direction actuelle est adaptée : **SwiftUI/MapKit + moteur ULog Python +
SQLite**, avec traitement local. L'import, la collecte, la déduplication,
l'identification manuelle et le rapport constituent une base utilisable.
Une réécriture du parseur en Swift n'est pas nécessaire pour les prochains lots.

L'installation utilisateur de **0.5.2 (7)** fonctionne sur macOS 27. La suite
doit surtout rendre l'historique durable, ses résultats cohérents entre écrans,
et les analyses assez complètes pour expliquer les observations de la flotte.
**500 identités ne qualifient pas encore plusieurs années de logs.**

Priorité proposée : **stabilisation 0.5.3 → sauvegarde/restauration → index et
périmètre partagé → événements et courbes → updater et qualification 0.6.0**.
Ces numéros désignent un découpage proposé ; aucune nouvelle release n'est créée.

## 5. Informations ULog : ce qui reste à exploiter

Le maximum récupérable dépend des topics et champs réellement enregistrés par le
firmware. Un champ absent doit rester absent. La configuration de logging PX4
détermine les données présentes dans un ULog. [PX4 — Logging](https://docs.px4.io/main/en/dev_log/logging)

| Donnée | Extraction actuelle | Extension proposée |
|---|---|---|
| Identité/provenance | SHA, taille, chemins, UUID ou fallback, identité GCS vérifiée | Identité canonique stable, disponibilité, réassociation par SHA, provenance datée |
| Date/temps | UTC GPS avec contrôles de cohérence ; sinon date de chemin ou inconnue | Instant UTC nullable séparé de la date calendrier/fuseau inconnu ; aucune conversion implicite |
| Messages | Textes et sévérités ; logged/tagged fusionnés | Conserver tag, type source et clé d'occurrence ; ordre source distinct du temps affiché |
| Événements PX4 | Nombre seulement | ID/arguments/timestamp/séquence/instance/niveaux interne et externe bruts ; traduction exacte si possible |
| Batterie | Min/max par instance : tension, courant, température, charge disponibles | Séries ; cellules, serial, cycles et états si présents. Serial batterie distinct du numéro drone |
| GNSS | Qualité temporelle par récepteur, satellites/précision, maxima bruts d'indicateurs | Séries par récepteur, âge RTCM si enregistré, lacunes/couverture ; états bruts expliqués selon firmware |
| GPS/carte | Récepteur choisi, 256 points aperçu / 4 096 détail, segmentation | Choix du récepteur, détail temporel à la demande, échantillons/segments omis annoncés |
| Paramètres | Valeurs initiales et changements dans la fiche | Types d'origine, différences traçables, inclusion optionnelle dans rapport détaillé |
| Topics/champs | Catalogue en détail | Catalogue typé avec instance/unité/provenance ; extraction de séries seulement à la demande |
| Métadonnées | Liste limitée, firmware et identité GCS | Infos multiples, boot console, compteurs performance et champs constructeur disponibles, inconnus préservés |
| Dropouts | Nombre et durée totale | Intervalles horodatés et lacunes visibles dans la chronologie |
| Failsafe/modes/états | Indicateurs et messages | Transitions horodatées, champs/cause enregistrés ; cause inconnue si non enregistrée |
| EKF/IMU/ESC/CPU/radio | Topics lisibles lorsqu'ils existent ; pas de courbes génériques | Recettes EKF prioritaires ; navigateur avancé de champs et analyses spécialisées ensuite |

`PX4Event` et `TelemetrySeries` sont des modèles préparatoires, pas une extraction
livrée. Le cache actuel ne remplace pas le fichier ULog original : les informations
non extraites ne sont plus récupérables si celui-ci disparaît.

Les niveaux interne/externe d'événement peuvent différer et les métadonnées de
traduction sont distinctes des événements. Le dictionnaire doit correspondre au
firmware ; aucun repli silencieux vers PX4 master. [PX4 — Events Interface](https://docs.px4.io/main/en/concept/events_interface)

## 6. Architecture et capacité

### Bibliothèque

- SQLite contient surtout des résumés JSON. Le snapshot décode tous les logs,
  messages et aperçus, puis SwiftUI recalcule les groupes/agrégats en mémoire.
- Le filtre de groupes reconstruit un ensemble de logs dans chaque groupe ;
  la croissance groupes × logs est établie par lecture, sans mesure de charge UI.
- La version de schéma DB et celle du JSON public sont couplées. Aucune chaîne
  complète sauvegarde/migration/retour arrière n'est disponible.
- Les annotations sont un JSON atomique ; deux instances peuvent s'écraser
  mutuellement. Aucun dommage de ce type n'a été observé. Deux versions de l'app
  sont présentes sur le poste : c'est un cas de recette à couvrir.
- Le verrou actuel des services protège le contrôle d'un processus ; il ne
  coordonne pas DB, annotations, réglages, archives et backup entre instances.

**Cible :** un coordinateur d'écriture, projections SQL reconstruisibles,
requêtes/pagination bornées, invalidation par révision et détails à la demande.
Le backup SQLite fournit une copie cohérente de la base ; les fichiers externes
doivent être capturés par la coordination KataLog. [SQLite — Online Backup](https://www.sqlite.org/backup.html)

### Collecte

Les protections existantes sont utiles : UUID autorisé, commandes limitées aux
logs, deux slots réservés avant suspension, un fichier par drone, validation
SHA/taille/en-tête/provenance, destination persistante par job, retries transitoires
bornés, absence de fallback silencieux dans Téléchargements.

À compléter :

- Un job pending hors ligne bloque Tout collecter pour de nouveaux drones
  connectés. Définir ajout à une session ou mise en attente explicite.
- Recherche de doublons quadratique, réécriture du JSON historique complet,
  inventaires séquentiels et réponse monolithique : capacité non mesurée.
- La validation SHA de tout le cache n'a pas de progression distincte. Le
  plafond de réponse côté service Swift doit borner les pages du protocole.
- SIGTERM fonctionne pour le helper normal testé. Un helper ignorant le signal
  pourrait bloquer l'arrêt : **hypothèse à tester**, puis délai/escalade/récolte
  du processus local. Ne pas présenter l'arrêt local comme l'arrêt FTP distant.
- Python accepte certains nombres finis là où Swift attend un Int ; isoler un
  appareil invalide plutôt que rejeter toute la découverte. Aucun cas réel observé.
- Sans request ID/empreinte distante, un remplacement distant de même chemin et
  taille n'est pas totalement détectable. Pas de reprise HTTP à l'octet ; ces
  limites restent visibles et ne seront pas promises sans support du protocole.

### Performance : distinguer les mesures

Le [benchmark du 29 septembre](BENCHMARK-500.md) rapporte 500 petits logs
synthétiques dérivés : import **15,911 s**, réimport **0,502 s**, mémoire moteur
environ **65,1/61,3 Mo**, snapshot **5,39 Mo**. Il n'est pas remesuré ici et
n'inclut ni rendu SwiftUI, ni navigateur, ni plusieurs années d'historique.

La cible proposée pour 0.6 est un index synthétique de **500 UUID, 50 000 logs et
5 millions de messages**, séparé du benchmark de parsing. Les budgets du
[plan §7](PLAN-0.6.0.md#7-bancs-et-objectifs-de-performance) sont à mesurer et à
qualifier, jamais à présenter comme des performances actuelles.

## 7. UX, rapports et explications

### Conserver et améliorer

- Conserver le bento noir/blanc, light/dark et les accents ponctuels approuvés.
- Ajouter une barre de périmètre lisible, sélection de drones recherchable,
  historique récent/paginé et vues enregistrées. La recherche ne doit pas rendre
  inaccessible le reset d'un filtre devenu vide.
- Le profil doit proposer les familles les plus fréquentes et un accès par clic
  aux logs concernés. Le radar garde l'ensemble et l'ordre des axes choisis,
  y compris leurs valeurs à zéro sous filtre ; un changement d'axes est annoncé.
  Le classement de fréquence est distinct de ces axes ; Autres reste inspectable.
- Séparer nombre de messages, logs concernés et drones observés. Ne pas nommer
  incidents une répétition de textes ni déclarer sain un drone sans données.
- Ajouter le mode système, les états zéro résultat/hors ligne/source absente et
  une recette de petites fenêtres. Les minimums actuels et grilles fixes limitent
  le confort ; aucune régression visuelle n'est affirmée sans cette recette.

### Rapport

Le HTML autonome, les thèmes, filtres, protection des textes et impression sont
à préserver. Il manque un contrat explicite sélection/bibliothèque, une
progression annulable, une fiche exportée plus complète et une stratégie de volume.
L'HTML actuel matérialise tous les messages dans le DOM et les données JSON.

Proposer **Synthèse flotte**, **Rapport de sélection** et **Fiche détaillée**,
avec prévisualisation du périmètre, des sections, des limites et de la taille.
Au-delà du budget navigateur, fournir une synthèse et des données complètes
jointes explicitement ; jamais une troncature discrète.

Ajouter un preset optionnel de partage qui masque chemins, identifiants et GPS
avec aperçu. Il ne garantit pas qu'un texte libre ne contient aucune donnée
personnelle ; aucune donnée n'est envoyée automatiquement.

### Explications et accessibilité

L'aide comporte peu de règles spécifiques. Chaque explication doit porter un
statut **Documentée / Interprétation / Inconnue**, une source/version applicable
et une limite. Une correspondance textuelle ne démontre pas une panne.

Recette à prévoir : navigation clavier/focus, VoiceOver, noms et états AX,
contrastes, augmentation de contraste/texte, Reduce Motion, fenêtre 1280×800,
thèmes et mode système. HTML : vrais tests DOM Safari/Chrome, impression, clavier,
sans JS et entrées Unicode/texte hostile. Les tests Node actuels ne suffisent pas.

**Toute nouvelle interface est maquettée et approuvée avant intégration.**

## 8. Distribution, confidentialité et qualité

- La distribution locale autonome est réalisée ; la recette macOS 15 reste à
  faire. Tests et minima Mach-O ne remplacent pas l'exécution sur cette version.
- Sparkle est pertinent pour les mises à jour hors App Store : feed HTTPS,
  signatures Ed25519, version de build croissante et bundle signé/notarisé.
  Le relancement doit attendre la fin/arrêt explicite des opérations.
  [Sparkle — Documentation](https://sparkle-project.org/documentation/)
- Le projet n'a pas encore de CI ni de licence racine. Choisir la licence avant
  ouverture si la redistribution open source est souhaitée. Un dépôt visible
  publiquement n'accorde pas seul toutes ces permissions.
  [GitHub — Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
- Figer source/build/parseur/schéma/runtime et hashes dans un manifeste de release.
  Auditer fichiers, historique, tags, assets compressés et captures avant visibilité.
- Ajouter About et diagnostic **local** avec versions et étapes échouées. L'export
  de support doit être borné et nettoyé ; aucun upload ou telemetry implicite.
- Étendre les tests des stores/services, notamment reload, annulation, concurrence,
  source absente, export pendant import et changements d'annotations.

## 9. Ordre de développement et portes de sortie

1. **0.5.3 proposée :** corriger les incohérences, ajouter leurs régressions et

5. **L7/L8 :** prototype updater tôt, intégration après coordination/backup ;
   qualification UI, performance, GCS et distribution, puis préparation publique.
